# Phase 3 briefing — self-imitation from RL-generated successes

Paste this as the opening message of a fresh session.

---

## Task

Build a **self-imitation dataset from the policy's own successful episodes** and
fine-tune on it. No human demonstrations and no external expert: every trajectory
is generated by checkpoints this campaign trained with RL.

Four parts:

1. **Record successes** from two checkpoints, staged from near-success starts out
   to the furthest state the model can still complete.
2. **Hindsight-relabel** each recording to every instruction it also satisfies.
3. **Smooth** the recorded action sequences, then **re-simulate and drop any
   episode that stops succeeding after smoothing.**
4. **SFT** on what survives.

### Scope decision, made deliberately

Phase 2's brief said "no demonstrations, no behaviour cloning". This phase
relaxes that, with a distinction that has to be stated in the writeup rather
than assumed: **the data is self-generated, so this is self-imitation (SIL), not
behaviour cloning from an external expert.** The RL-only result stands on its own
and remains the headline contribution; this phase is an extension, and its
numbers must be reported separately from the RL-only ones, never merged into
them.

## Setup

* **Robot**: cable-driven parallel robot. 5-D action `(x, y, z, yaw, gripper)` in
  `[-1,1]`, scaled 0.015 m / 0.08 rad / 0.05 opening per env step. The controller
  target is **re-anchored to the measured EE pose every step** — this matters for
  smoothing, see below. Workspace xy ±0.19 (camera-bounded), z [0.19, 0.32];
  objects rest at z ≈ 0.19–0.21.
* **Policy**: frozen SmolVLA prior + trainable residual MLP (1024 hidden) + LoRA
  on the action expert. `action = tanh(prior + residual)`.
* **Sim**: MuJoCo Warp, 512 worlds/rank × 2 ranks.
* **Config**: `configs/examples/cdpr_smolvla_catch_release_dense_grpo_mjlab_resume.yaml`
* **Run**: remote 2×A40, `conda run -n cdpr-mjlab`, always with
  `RLVLA_HF_OFFLINE=1 MUJOCO_GL=egl`. I run things; you write and push. Always
  `git commit && git push` when done.

## What is already measured — do not re-derive

Held-out validation of the placement checkpoint, by start-distance cap
(`tools/audit/xy_approach_probe.py --legs policy --start-distance-cap X`):

| cap | plate | bowl | pick_up |
|---|---|---|---|
| 0.01 | 0.943 | 0.857 | 0.089 |
| 0.03 | 0.898 | 0.821 | 0.054 |
| 0.06 | 0.852 | 0.821 | 0.030 |
| 0.10 | 0.443 | 0.435 | 0.030 |

**This table is the recording plan.** Stage the collection along it: the near
rungs yield successes cheaply and safely, 0.10 yields few and biased ones.

In training the same checkpoint's successor reached plate **0.830** peak
(0.78–0.83 sustained over 3M steps, converged) and bowl ~0.40, with the bowl at
**0.672** while its cap was still 0.06.

Other established facts:

* **The frozen encoder localizes to 3–5 cm.** That is fatal at pick_up's ~2 cm
  grasp tolerance and survivable at placement's 0.057/0.091 m radii — the oracle
  ladder retains 88% of ceiling at 3 cm and 68% at 5 cm. The limit is a tolerance
  mismatch, not a general ceiling.
* **Rehearsal does not protect a skill.** pick_up was kept in the phase-2 mix
  specifically to preserve the phase-1 grasp and was forgotten anyway — 0.183 →
  0.027 at matched cap, `physical_grasp_rate` 0.664 → 0.148. Assume interference,
  not capacity, until measured.
* The realized XY gain is **~0.0075 m per env step**, half the nominal
  `action_step_xyz`. Any horizon arithmetic assuming 0.015 is wrong.
* `robocasa_banana` and `robocasa_mug` are excluded as targets: bracketed from a
  fully open gripper both contact at 0.98, i.e. they are wider than the gripper's
  open gap in the seeded pose.

## Hindsight relabeling — what exists and what does not

`ACTIVE_INSTRUCTION_TYPES` is a **fixed-width id table** shared with the MJWarp
schema:

```
move_to_object, push_left, push_right, put_into_bowl, put_into_plate,
move_left_of_object, move_right_of_object, move_between_objects, pick_up
```

So of the relabelings requested:

* "push left / push right" — **exist**.
* "push forward / backward" — **do not exist.** Adding them is a schema change to
  a fixed-width table, not a config edit. Price it before promising it.
* "put near / to the left of / to the right of the plate/bowl" —
  `move_to_object`, `move_left_of_object`, `move_right_of_object` exist and take
  a reference object, so these are expressible.
* "pick up the object" as a prefix of "put object into plate/bowl" — this is the
  strongest relabel in the set and the one to build first.

There is existing hindsight machinery in `rl_vla_bootstrapping/lchol/`
(`grpo_runtime.py`, `replay_buffers.py`, `curriculum.py`). It is **disabled** in
the phase-2 config, not absent. Read it before writing anything new.

**Relabel against the production success predicate, never by hand.**
`evaluate_active_sparse_tasks` in `rl_vla_bootstrapping/simulation/cdpr_batched_tasks.py`
is the only thing that decides whether a trajectory satisfies an instruction. A
second implementation will drift from it, and this campaign has been bitten by
exactly that class of duplication more than once.

## Smoothing — the specific risk

The controller **re-anchors its target to the measured EE pose every step**. A
smoothed action sequence is therefore not guaranteed to reproduce the recorded
trajectory: the plant is closed-loop around a pose the smoothed actions no longer
visit. This is why part 3 requires re-simulation rather than trusting the
smoothed sequence.

Concretely: replay every smoothed episode through the same backend, re-score it
with the production predicate, and keep only what still succeeds. Report the
survival rate per smoothing method — that number is the method's real quality
metric, not trajectory-space smoothness.

## Traps this campaign actually fell into. Check for each.

1. **Knobs that read from nowhere.** `target_object_pool` is not read on the
   MJWarp path — editing it excluded nothing and the object kept being trained
   on. `grpo_min_group_reward_std` was set in one config and not another, and the
   GRPO noise filter was silently off for three runs.
   `tools/audit/xy_approach_probe.py` rebuilt its argument namespace from the
   *checkpoint*, so it ran pick_up episodes while claiming to measure placement.
   **Verify a new knob changes a measured quantity before trusting it.**
2. **Gates the reset already satisfies.** The placement promote gate read the
   grasp rate, and placement starts already grasped — so it was open on every
   update and the cap ran to its ceiling while success was exactly 0 for 5M
   steps. Separately, the first curriculum rung sat *inside* the success radius,
   so "success" was the reset, not the policy.
3. **Budgets coupled to the wrong quantity.** The horizon is coupled to the
   approach cap, which knows nothing about a grasp prefix that costs ~30 env
   steps regardless of distance.
4. **Controls that are not nulls.** `--release-opening-threshold` also changed
   the oracle's own target opening, so lowering it weakened the oracle instead of
   loosening the reward.
5. **Selection bias, which this phase turns into a training signal.** Selecting
   on success selects on alignment for any policy, including a blind one. At the
   plate's 0.85+ that is fairly safe; at pick_up's 0.03–0.18 a large share of the
   kept episodes are lucky rather than skilful. **Report the source success rate
   next to every dataset slice**, and consider whether a slice below ~0.2 should
   be used at all.
6. **CPU vs MJWarp.** Contact-dependent constants differ by 0.02–0.04 between the
   engines. Anything measured from contact must be measured on MJWarp.

## Tools that already exist — extend rather than duplicate

* `scripts/render_cdpr_task_reference_episodes.py` — production resetter +
  production reward + the trainer's own `_update_physical_grasp` under a scripted
  oracle. Renders video, writes per-step telemetry and a manifest. Has
  `--start-distance-cap`, `--metadata-override`, `--reseat-held-object`,
  `--physics {mjlab_mjwarp,mujoco_cpu}`. **This is the replay-and-rescore harness
  for part 3.**
* `tools/audit/xy_approach_probe.py` — builds the full training stack from a
  checkpoint and runs the trainer's own `validate_round` with the action or the
  residual's input substituted. Legs `plant`, `policy`, `oracle`, `ablation`,
  `placement`. Reports success per instruction. **This is the recording harness
  for parts 1–2**, since it already runs a deterministic policy through
  production resets and keeps a per-decision trace (`policy_trace.npz`).
* `rl_vla_bootstrapping/lchol/` — hindsight relabeling and replay buffers,
  currently disabled.
* `training.sft` in the config — an SFT stage exists and is set `enabled: false`.

## First deliverable

Do **not** start collecting yet. First:

1. Confirm the recording path end to end on a *small* sample — say 32 episodes at
   cap 0.01 for `put_into_plate` — and show that a recorded episode replayed
   through `render_cdpr_task_reference_episodes.py` reproduces the same success
   verdict. If a recording cannot be replayed, nothing downstream is valid.
2. Report what fraction of episodes survive replay before any smoothing. That is
   the floor; smoothing can only lower it.

State up front what each measurement would show and what result would falsify it.

## How I work

Be sceptical of my framing and of your own conclusions. Over ~25 runs the
recurring failure has not been bad ideas — it has been measurements that were
technically correct but did not imply what we thought, and conclusions drawn from
a control that was not a null. Several confident interventions were reverted.
When a result contradicts a claim you made earlier, say so plainly and correct it.
