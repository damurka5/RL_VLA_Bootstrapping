# Simulator choice: stay on MuJoCo, then batch it on MJWarp (June – July 2026)

This file merges the two simulator reports from 2026-06-06, plus the
comparator run that went with them:

- `MUJOCO_SETUP_CLEANUP_REPORT.md`, which instrumented and cleaned up the CPU MuJoCo setup
- `SIMULATOR_MIGRATION_DECISION_REPORT.md`, which weighed staying against migrating
- `tools/sim_compare/out/SIMULATOR_COMPARATOR_REPORT.md`, generated by the comparator tool

The originals are in [`legacy/`](legacy/) and in git history (commit `9339dd9`,
which also keeps the `tools/sim_compare/` comparator and its outputs). The

## The question

In June 2026 training ran on one CPU MuJoCo environment per GPU rank. Rollouts
were slow, YCB objects shook and slipped in the gripper, and every reset
recompiled the model. Should the project move to ManiSkill/SAPIEN, Isaac Lab,
robosuite/RoboCasa or a benchmark suite such as RoboTwin?

## What was measured

| Measurement | Result |
|---|---|
| Same-topology reset, no model cache | 104 ms mean (compile ≈ 100 ms) |
| Same-topology reset, compiled-model cache | 4.6 ms p95, 99% hit rate |
| Physics step | ≈ 0.27 ms, no-render ≈ 3,700 FPS |
| Contact stability, stable primitive pack | 31/35 checks pass. Drop, rest and push pass for every object; block and can fail squeeze/lift because the fingers do not reach them |
| Earlier YCB gripper tests | Normal-force spikes of 1.6k–28k N (mesh-based COACD collision) |
| Comparator (seed 20260606) | Raw CDPR MuJoCo: 9,234 physics steps/s, stability 1.0, 140/140 scripted task rows. ManiSkill, Isaac, robosuite and PyBullet were not installed and were not measured |
| Two-camera render/readback | Could not be measured on the macOS host |

The decision matrix scored raw MuJoCo highest on custom CDPR kinematics,
custom controllers, migration effort and scientific risk. It scored lowest on
rendering and parallel-rollout throughput, which is where ManiSkill and Isaac
were strongest.

## Decision

**`STAY_ON_MUJOCO_REFACTOR_FIRST`.** The evidence pointed at how the project
used MuJoCo, not at MuJoCo itself: wrapper files, per-episode recompilation,
texture variants and mesh collision. Migration would be reconsidered only if a
refactored MuJoCo still could not meet throughput or stability needs, or if a
candidate showed a clear >3× rollout gain at acceptable porting cost.

## What happened next

The throughput problem was solved inside the MuJoCo family. In July 2026 the
project added a **rank-local batched MJWarp backend through MJ-Lab**: one
fixed-shape GPU `Model`/`Data` per rank, complete GRPO groups on one rank, and
images kept as CUDA tensors. Simple stable objects and RoboCasa produce
replaced the unstable YCB meshes. Every later result in the
[consolidated report](../../../CDPR_CONSOLIDATED_PROGRESS_REPORT.md) was
trained on that backend, with 512 worlds per rank on 2× A40.
